Intra-Segment Parallel IVF Scoring

This PR lets multiple worker threads scan one segment's IVF posting lists in parallel — for every IVF query variant (plain, sliced, diversified, diversified+sliced) and for merge-sliced segments — while guaranteeing recall is at least what the serial scan produces. It also fixes a pre-existing recall bug in the diversified collector's score-floor publishing.
branch parallel-ivf-scoring-poc on by default — sysprops are runtime kill switches no format change · no API change

Why this PR exists

Vector search in Elasticsearch runs one task per segment. That parallelizes nicely across segments — but after a force_merge (the recommended setup for vector-heavy indices) there is exactly one segment, so a kNN query uses exactly one thread no matter how large the search pool is. Inside that segment, the IVF scan visits ranked posting lists strictly one after another.

The fix: split the within-segment scan across workers. Prior measurements on single-segment indices showed roughly 2× lower latency from this kind of parallelism, and a JMH benchmark in this PR (IndexInputCloneScanBenchmark) proves the foundation is sound: per-worker IndexInput slices off one shared mmap arena scale identically to independently opened files.

The one-line mental model: rank all posting lists by how promising their centroid is (unchanged), then let W workers claim chunks of that ranked list from a shared atomic cursor and score them with completely private state — merging results at the end, and handing anything unclaimed back to the original serial loop so nothing that would have been visited is ever skipped.

What you get

  • Latency, not throughput: the same total scoring work finishes on W threads. Worker count is a latency↔CPU dial.
  • Recall ≥ serial, by construction: the parallel run visits a superset of the serial run's postings.
  • At visit_ratio = 1.0 results are identical to serial (up to reordering of exactly tied scores).

The three-phase design in one picture

1 · DRAIN (leaf thread) Pull the visit budget's worth of ranked postings (×1.25 overshoot) out of the centroid iterator into a plain array. Prefetch the head.
→
2 · CLAIM & SCORE (W workers) Workers grab shrinking chunks off one atomic cursor, score them with private visitors/collectors, share only a score floor. Stop when the budget is covered.
→
3 · CONTINUE (leaf thread) Merge worker results into the leaf collector; hand unclaimed postings back to the unmodified serial loops, which resume under their exact original conditions.

Phase 3 is the correctness anchor: because claimed chunks are always scanned to completion and everything unclaimed remains visible to the serial continuation, the set of visited postings is a superset of what the serial algorithm would have visited. See the interactive walkthrough.

IVF in 60 seconds — just enough to read this PR

IVF (inverted file) vector search clusters the segment's vectors at index time. Each cluster has a centroid (its mean vector) and a posting list (the quantized vectors of its members, stored contiguously on disk).

A query then does two things:

  1. Rank centroids — score the query against every centroid (cheap: int7-quantized, SIMD) and sort posting lists from most to least promising.
  2. Scan posting lists in that order — score the query against each member vector (1-bit quantized + corrections, SIMD bulk kernels), feeding a top-k collector, until a visit budget is spent: maxVectorsVisited = 2 × visitRatio × numVectors.

The ×2 exists because of SOAR: each vector may appear in up to two posting lists (its closest centroid plus one "spilled" assignment), improving recall at the cluster boundary.

Four terms you'll see everywhere

TermWhat it is
PostingMetadata A self-describing handle to one posting list: file offset, length, which parent centroid to quantize the query against, and the centroid's score. Everything a scorer needs to visit that list, independent of any other list — this independence is what makes parallelism possible.
CentroidIterator Streams PostingMetadata in descending centroid-score order (best cluster first). Normally wrapped in a PrefetchingCentroidIterator that hints the OS to read ahead.
PostingVisitor The codec's scoring machine: resetPostingsScorer(metadata) seeks to a posting list, then visit(collector) bulk-scores members into a collector using SIMD kernels, block-level filter skipping and adaptive pruning. Holds mutable scratch — never shareable between threads.
Min-competitive floor Once a top-k collector is full, its worst kept score is a floor: candidates below it can't matter. The codec prunes whole blocks against this floor. Collectors exchange floors through a LongAccumulator (an atomic max), publishing once per posting list via nextVectorsBlock().
Why the serial scan is safe to split: per-document scores are deterministic and every posting list is independently addressable via its PostingMetadata. The only cross-posting state in the serial loop is (a) the visit-budget counter and (b) the collector + its score floor. The scanner makes (a) an atomic total and (b) private per-worker collectors coupled only through the atomic floor — everything else is thread-confined by construction.

Class map — who talks to whom

Solid arrows = calls / creates. Dashed = "travels inside" (the context rides on the strategy, the strategy rides on the collector). The strategy is the only bridge the codec sees — codec code never imports query classes, and query code never sees codec scoring types.

The factory pattern is the key extensibility move of this PR. Before, the scanner hardcoded a plain top-k collector for every worker — which is wrong for diversified queries (workers would keep k children of one parent and starve other parents, and publish inflated score floors). Now IVFKnnSearchStrategy.newParallelWorkerCollector asks the leaf collector to mint the worker, so a diversifying leaf gets diversifying workers (sharing its read-only parent bitset) and a plain leaf gets plain workers. The codec never knows the difference.

The claim loop, step by step

A scaled-down segment: 22 ranked posting lists (greener = higher centroid score), 3 workers, and a visit budget that covers roughly the best 16 lists. Press Step to advance, or Auto to play.

Chunk size formula
min(8, budgetLeft/avgDocs, remaining/(4·W))
Chunks shrink as the array drains (stragglers bounded by one posting) and as the budget nears (overshoot stays small).
Double-buffered prefetch
A worker claims (and OS-prefetches) its next chunk before scoring the current one, so disk read-ahead overlaps scoring.
Why overshoot is fine
A claimed chunk is always scanned to completion — visiting more than serial can only help recall. The budget check stops new claims, not in-flight ones.

Low-level walkthrough — one leaf, gate to merge

query layerstrategy / collectorscodec
1
AbstractIVFKnnVectorQuery · once per query

Resolve the worker budget

resolveIntraSegmentParallelism() runs in rewrite(): master sysprop on → count leaves that contain the field → if the searcher is a ContextIndexSearcher with an executor, maxWorkers = min(8, max(1, maxSlices / leavesWithField)) — dividing the request-level concurrency budget across leaves so leaf tasks plus intra-segment workers never oversubscribe the search pool. Needs ≥ 2 to proceed. Plain IndexSearcher harnesses (checkVec) use the force property instead. Result: an IVFParallelismConfig(taskExecutor, maxWorkers, checkCancelled), where checkCancelled is the searcher's timeout/cancellation hook.

2
IVFKnnFloatVectorQuery · per leaf

Build acceptDocs, strategy, context, collector

getLeafResults() wraps live docs / the filter scorer into an ESAcceptDocs. approximateSearch() then builds the IVFKnnSearchStrategy(visitRatio, numCands, k, accumulator, newParallelScanContext(manager)). The context's workerAccumulator is the collector manager's accumulator when one exists, else a fresh one — so workers always prune against each other. The manager creates the leaf collector (MaxScoreTopKnnCollector, or DiversifyingNearestChildrenKnnCollector with the parent bitset fetched here, on the leaf thread) and strategy.setCollector() registers it — the strategy is now the bridge that carries everything into the codec.

3
IVFVectorsReader.search · leaf thread

Gate checks + filter materialization — all before any fork

Compute the visit ratio (the dynamic Two-Signal model if unset) and the budget maxVectorsVisited = 2 · visitRatio · numVectors. If the strategy carries a parallel context, ask the format: getParallelScanSupport(...). Base returns null (serial); ESNext returns a raw, non-prefetching centroid iterator (a FlatCentroidIndex that scored every centroid with SIMD int7 kernels) plus approxBytesPerVector to size the drain. Crucially, acceptDocs.bits() is called now — fully consuming any one-shot filter iterator on this thread and materializing a read-only bitset that workers can share safely.

Why a raw iterator? The normal prefetch wrapper reads ahead as you consume. Draining hundreds of postings through it would fire a burst of prefetches for data consumed much later. The scanner prefetches per claimed chunk instead — right before scoring.
4
ParallelPostingListScanner.scan · leaf thread

DRAIN — turn the iterator into a claimable array

Pop ranked PostingMetadata until drainedBytes ≥ 1.25 × budget × bytesPerVector (the 1.25 overshoot means the serial continuation rarely needs the live iterator again). The first W × 8 postings get an eager prefetch so the earliest chunks are already being read while workers spin up. Then decide: workers = min(maxWorkers, drained / 4). Fewer than 2 → no worker state is ever created; everything drained is handed back, prefetch-wrapped, to the serial loop. This is the "not enough work" bail-out.

5
Lucene TaskExecutor

Fork W workers — deadlock-free by design

invokeAll(tasks) submits W callables to the search pool. Lucene's TaskExecutor also runs queued tasks on the calling thread, so a saturated pool degrades to caller-runs instead of deadlocking — the query thread always contributes to its own scan. Worker count is purely a latency ↔ CPU dial; total work is unchanged.

6
worker thread · startup

Thread-confined state, minted where it's used

Each worker first calls the WorkerStateFactory — on its own thread — creating a fresh postings IndexInput slice and a fresh PostingVisitor (its own query quantizer, scorer, scratch buffers). Then strategy.newParallelWorkerCollector(k, visitLimit): builds a worker strategy sharing the context's workerAccumulator, and asks the leaf collector to mint a private twin of its own shape (AbstractMaxScoreKnnCollector.newParallelWorkerCollector — the new polymorphic factory). Nothing mutable is shared on the scoring path; the JMH benchmark in this PR verified the slice-per-worker pattern has zero arena contention.

7
worker thread · steady state

The claim loop

int[] current = claimAndPrefetch(input);          // cursor.getAndAdd(size) + OS prefetch
while (current != null) {
    checkCancelled.run();                          // timeout/cancel observed between chunks
    int[] next = claimAndPrefetch(input);          // double-buffer: prefetch NEXT before scoring CURRENT
    score(visitor, collector, current);            // per posting: resetPostingsScorer → visit → nextVectorsBlock
    current = next;
}

Chunk size = min(8, budgetLeft/avgDocsPerPosting, remaining/(4·W)) — shrinking so stragglers are bounded by a single posting and budget overshoot stays small. Per-chunk, expected/actual doc counts are accumulated locally and flushed with one atomic add — one shared RMW per chunk, not per posting. claimAndPrefetch returns null once expectedDocsTotal ≥ budget: no new claims, but in-flight chunks always finish.

8
IVFKnnSearchStrategy.nextVectorsBlock · once per posting list

Score-floor gossip

Each collector's guarded floor (only full heaps publish — the bug fix) goes into the shared LongAccumulator via atomic max; the encoding is score-major with a doc-id tiebreak, so Long::max orders correctly. The worker then pulls the accumulator back and raises its own floor if someone else's is higher. The codec's bulk kernels prune whole blocks against minCompetitiveSimilarity() — this is how one worker's good results speed up the others.

9
ParallelPostingListScanner · leaf thread, after invokeAll joins

MERGE — private results into the leaf collector

For each worker: fold its visited count, then drain its top-k — unsortedTopK() + bulkCollect() for plain (bulk heap insert), or topDocs() + per-doc collect() for diversifying workers, which re-runs the per-parent max-wins dedup in the leaf collector. Merging after invokeAll gives the happens-before edge; order can't matter because every merge op is max-wins.

10
IVFVectorsReader.search · leaf thread

CONTINUE — the original serial loops, untouched

The scanner hands back remainingIterator = unclaimed drained postings ⧺ the live iterator, wrapped in a lazy prefetcher (no wasted I/O on the common path where the budget is already covered). The two pre-existing loops then run verbatim: the unfiltered loop (while budget not covered || collector not full) and the filtered adaptive loop (while actualDocs < expectedScored || actualDocs < k) — seeded with the workers' aggregated expected/actual counts. This is the superset guarantee: every posting the serial algorithm would have visited is either fully scored by a worker or still visible here.

11
AbstractIVFKnnVectorQuery · back at the query layer

Dedup and merge as always

searchLeaf() maps doc ids to global space and dedups SOAR copies keeping the best-scoring copy (changed from first-wins so drain order can't affect results), then all leaves merge into the shard's top-mergeK. Nothing downstream knows workers existed.

Sliced: two different "slice" concepts

Don't confuse the query-level slicing above with the codec-level numSlices in the ESNext format — the PR touches both:

numSlicesMeaningParallel?
-1Not sliced (no slice field configured) ✔ (was already)
0Flush-sliced: written at flush with a slice field — has exactly one centroid (asserted), and its visitor resolves slice doc-ranges through a lazily-cached walk of a shared DocValuesSkipper ✘ hard-gated: nothing to parallelize (one posting list) and the lazy cache must stay on the leaf thread

Diversified: why the factory matters

Before — hardcoded plain workers (broken for diversified)

  • A worker's plain top-k can hold k children of one parent; children of other parents that would survive the per-parent dedup are evicted and lost forever → recall loss.
  • A plain worker's floor is its k-th child score — always ≥ the k-th parent score. Published into the shared accumulator it over-prunes every other worker.

After — leaf collector mints the worker

  • DiversifyingNearestChildrenKnnCollector.newParallelWorkerCollector() returns another diversifying collector sharing the same parent bitset (fetched once on the leaf thread; workers only read it; invokeAll publishes it safely).
  • Worker floors are k-th parent floors — valid by the same argument as the leaf's.
  • Merge: each worker's per-parent bests are collect()-ed into the leaf collector, whose heap keeps the max per parent — insertion order provably irrelevant.

Why the merge is exact (the eviction argument)

Could a worker evict a parent that belongs in the final top-k? No: the per-parent heap's minimum is monotonically non-decreasing once full — an entry is only ever replaced by something strictly better. So if worker w evicted parent X at score s, then w ends holding k parents all scoring ≥ s, and all k reach the merge. X (best child ≤ s) can therefore never be in the merged top-k anyway. The same argument covers plain top-k workers — it's the standard "merge of local top-k's" proof, applied per parent.

k means parents here. For diversified queries the collector budget counts parents, not children — worker collectors inherit the same k from the leaf collector, so the shapes line up by construction.

The correctness contract

InvariantWhy it holds
Visited set ⊇ serial's visited set Workers only consume ranked postings from the front (the exact prefix serial would take); claimed chunks always finish; everything unclaimed is re-fed to the unmodified serial loops with the workers' counts pre-seeded. Extra visits (budget overshoot) can only add candidates.
Per-doc scores are bit-identical Scoring math has no cross-posting state; each worker's visitor/quantizer produces the same score for the same (doc, posting) pair as the serial visitor would.
Result set at visit_ratio 1.0 ≡ serial Both visit everything; scores identical; top-k of the same multiset. Only runs of exactly tied scores may permute (block pruning compares scores only; heap ordering tiebreaks on doc id — floor propagation timing can reorder ties). The tests compare rank-for-rank scores and tie-run doc sets.
Partial budget: parallel k-th score ≥ serial k-th score Direct consequence of superset visiting + identical per-doc scores.
Floors never over-prune Only full heaps publish (see bug fix below); a full heap's floor certifies k collected results ≥ s, which is a valid lower bound wherever it travels. Atomic max keeps the accumulator monotone.
Order independence of merges Every merge op is max-wins: SOAR dedup keeps the best copy, the diversified heap keeps the best child per parent, top-k heaps keep the best k. No first-wins step survives in the pipeline.

BUGFIX The diversified min-competitive guard

The diversified collector published its heap top as a pruning floor whenever the heap was non-empty — but an under-filled heap's top is just "the worst parent seen so far", not a bound on the k-th best. The plain collector always had the guard; the diversified one didn't:

- return heap.size() > 0
-     ? max(encodeRaw(heap.topNode(), heap.topScore()), minCompetitiveDocScore)
-     : minCompetitiveDocScore;
+ // Only a full heap's top is a valid bound on the k-th best parent
+ return heap.size() >= k()
+     ? max(encodeRaw(heap.topNode(), heap.topScore()), minCompetitiveDocScore)
+     : minCompetitiveDocScore;

(Same guard added to the fold-back side, updateMinCompetitiveDocScore.)

The poisoning mechanism (pre-fix)

  1. Early posting collects one great child (score 0.9); heap has 1 of k parents → publishes 0.9 as a "floor" into the accumulator.
  2. More parents arrive, heap top drops to 0.5 → the accumulator (still 0.9) is folded back into the collector — and the fold is max-monotonic, so it sticks forever.
  3. Heap finally fills at k parents, true floor 0.2 — but minCompetitiveSimilarity() now returns max(0.9, 0.2) = 0.9.
  4. The codec skips every block whose best possible score < 0.9 → parents that should replace heap entries (scores 0.2–0.9) are silently never scored. Recall loss with no error signal.

Reachable today on any multi-segment diversified query (the accumulator only exists with > 1 leaves) — and parallel workers would have amplified it badly, since every worker starts with an empty heap. The deterministic regression test was verified to fail before the fix by temporarily reverting it.
